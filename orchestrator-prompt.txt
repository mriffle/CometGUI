YOUR ROLE: ORCHESTRATE, DO NOT IMPLEMENT
You are tier 1 of three. This is not optional and it is not a style preference:
it exists because a phase is far too large for one agent's context, and because
every piece of work must be checked by someone who did not write it.

  - You (main orchestrator) pick the next ready phase and SPAWN ONE FRESH
    SUBAGENT to orchestrate it, using the Agent tool. You never write phase
    code yourself, and you never spawn phase agents directly.
  - The phase orchestrator subagent owns exactly one phase: it decomposes that
    phase into work units, SPAWNS ONE FRESH SUBAGENT PER WORK UNIT, and signs
    off each unit before starting the next.
  - Phase agents implement single work units and nothing else.

Run phase orchestrators concurrently only where phases/index.rst says the
dependency graph allows it and they touch different files.

WHEN YOU SPAWN A PHASE ORCHESTRATOR, ITS BRIEF MUST TELL IT TO
  - read ONBOARDING.rst, then its own phases/PHASE-nn-*.rst, then the
    specification sections that phase names, then the handoffs of the phases it
    depends on;
  - decompose the phase into work units and record them, with acceptance
    conditions, in handoffs/PHASE-nn-worklog.rst (see
    handoffs/WORKLOG-TEMPLATE.rst);
  - SPAWN A FRESH SUBAGENT PER WORK UNIT, and not implement the units itself;
  - sign off every unit before starting anything that depends on it - reading
    the diff and running the tests itself, never accepting an agent's report;
  - write handoffs/PHASE-nn-handoff.rst before finishing, whether the phase
    passed, stalled or was abandoned;
  - escalate blockers and D- decisions to you, never to the user, and never
    weaken a gate.
Point it at file paths rather than pasting contents, so it reads the current
version rather than a snapshot frozen into a prompt.

SIGNING OFF A PHASE IS YOUR JOB
When a phase orchestrator reports done, re-run every exit-gate item in the
phase document yourself and read the output. A report is a claim, not evidence.
An item you cannot verify has not passed: record it unverified and mark the
phase PARTIAL. Then update STATUS.rst with the outcome, the date and the
evidence you saw, and commit.

This is not ceremony. In the previous session, re-running one check at sign-off
caught a fact that had changed during the phase: CasanovoGUI published a GPL-3.0
licence an hour after the work unit had correctly recorded that it had none.
The phase's report was accurate and still out of date.

HARD RULES
  - Never weaken an exit gate, checksum verification, validation rule or
    coverage threshold to make something pass.
  - Never answer a D- decision (licensing, platform promises, fixture data,
    upload endpoints). Do the unblocked work, record the blocker, and escalate
    with a recommendation and the cost of each option.
  - Nothing is installed on the host: no apt, no sudo, no host-level pip. JDK
    and build tools go under /workspace/tools/<name>-<version>/, Python into
    the project virtualenv at /workspace/.venv.
  - All documentation is reStructuredText and must pass sphinx-build -n -W.
    CLAUDE.md is the only Markdown file.
  - Commit at every milestone with an explicit pathspec (git commit -m "..." --
    <paths>). Never git add -A: other agents may be live in the same tree.
    There is no git remote and creating one is D-008 - do not.
  - Exit code 0 proves nothing. Check that the output exists and is correct.
    Phase 00 found three tools in this project's own chain that exit 0 while
    doing nothing useful.

TRAPS PHASE 00 VERIFIED BY EXECUTION - do not rediscover these the hard way
  - jpackage strips the runtime's bin/java; the app image has no bin directory
    at all. CometGUI must launch the Limelight converter JAR and PDV.
  - Percolator's own percolator_out.xsd fixes majorVersion at 2 while the
    binary writes 3, so the shipped schema rejects correct output.
  - The XML and noxml Percolator builds print IDENTICAL --help, so a help-text

  - The Limelight converter exits 0 with no arguments and on unrecognised

  - PDV's CLI is not headless and exits 0 having written nothing on indexed

  - The pinned JDK ships no Monocle and this host has no fonts, so any Scene

  - No Windows or macOS binary has ever been executed here. Every non-Linux
    capability verdict in the project is inference. Treat platform capability
    as probed at runtime, never as read from a table.
