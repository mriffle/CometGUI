What this work is, and what it is not
=====================================

Two gate items were left ``PARTIAL`` for one reason each, and both reasons
were the same missing thing -- a git remote:

**PHASE-00, gate item 8, first branch.** No Windows binary in this project has
ever been executed. Every non-Linux capability statement is inference from
byte markers, and ``docs/feasibility/windows-artefact.rst`` says so in its
opening warning.

**PHASE-01, gate item 6.** The three workflow files exist and all 42 of their
steps have been executed locally by ``scripts/ci/run-pipeline-locally.sh``,
but GitHub has never executed them, because there was nowhere to push.

``D-008`` was decided on 2026-08-30 and ``origin`` now exists. The two items
compose: a branch that adds a Windows verification workflow, opened as a pull
request, exercises the pull-request pipeline (item 6) while carrying the job
that produces the Windows evidence (item 8).

**This work cannot close either item, and does not claim to.** This session
has no push credential of any kind: no ``gh``, no ``GH_TOKEN``, no SSH key, no
credential helper. ``git push`` fails with ``could not read Username``. What
this work produces is a branch, committed locally, that makes closure a matter
of the owner pushing and the runners executing. Until a runner has executed
it:

* ``xml_capability`` in the tool manifest stays ``unverified-on-windows``;
* the basis keeps the sentence "The binary was not executed on Windows.";
* the words *verified*, *confirmed*, *proven* and *tested* are not used of the
  Windows binary anywhere;
* ``docs/feasibility/windows-artefact.rst`` is not rewritten as though the run
  had happened.

The seven-step checklist being automated is the one in that document's section
"Recommended: the checklist for a Windows machine", and its last line is the
requirement this work is measured against: *"Return the transcript. It replaces
this document's central caveat with a fact, either way."* A job engineered to
go green would fail that sentence. The harness must be able to report a
negative honestly, and must fail loudly when it does.

U1 -- one synthetic PIN generator, not two
==========================================

:Serves: PHASE-00 gate item 8 (the ``-X`` and ``--xml-in`` tests need an input)
:Wave: A

The 400-PSM synthetic PIN is generated by a Python heredoc inside
``scripts/feasibility/windows-artefact.sh`` (lines 186-201). The Windows runner
needs the same input. Two copies of a generator is two things that drift, and
a comparison between platforms is worthless if the inputs differ.

Acceptance conditions
---------------------

#. ``scripts/feasibility/make_synthetic_pin.py`` exists, is executable, uses
   only the standard library, and takes an output path.
#. Its output is **byte-identical** to what the heredoc produces today.
   Measured before the change: SHA-256
   ``6643ede48534fcd28c90a1d4e53781e47ba39b0523e9f907ea8e1a63b15af61e``,
   32 466 bytes, 401 lines. That constant is pinned in the generator and
   checkable with a flag.
#. ``windows-artefact.sh`` calls the generator instead of carrying the
   heredoc, and still runs end to end.
#. The generator cannot produce different bytes on Windows **by construction**
   for the one reason that would otherwise be certain: text-mode newline
   translation. It writes with an explicit newline, never the platform
   default.
#. The remaining cross-platform risk -- ``random.gauss`` calling ``libm`` --
   is measured, not asserted, and the measurement is recorded in the file.
#. No project gate, checksum or rule is weakened.

U2 -- does ``extract_nsis.py`` really run on Windows unchanged?
==============================================================

:Serves: PHASE-00 gate item 8, step 2 of the checklist
:Wave: A

``docs/feasibility/windows-artefact.rst`` claims twice that the extractor "is
pure Python and runs on Windows unchanged". That claim has never been tested;
the checklist's second step depends on it entirely.

Acceptance conditions
---------------------

#. Every POSIX-only assumption in the file is found and named with a line
   number: path separators, hardcoded ``/``, ``os.chmod``, ``os.path`` versus
   ``pathlib`` mixing, shell-outs, ``open()`` without an explicit mode or
   encoding, ``os.access``, ``/tmp``, symlink handling, and reserved Windows
   filenames.
#. Each finding is classified: **breaks on Windows**, **behaves differently on
   Windows**, or **harmless**, with the reasoning.
#. Anything in the first two classes is fixed minimally, without changing
   behaviour on Linux.
#. The fix is proved on Linux by a test that fails without it -- for example,
   an extraction driven through ``ntpath`` semantics, or a payload whose
   member paths use backslashes.
#. After the change, ``bash scripts/feasibility/windows-artefact.sh`` still
   reproduces the same extraction: ``percolator.exe``
   ``044f3957e2f05a38d13d8c77136f24435827d8563850b8808b5ad52e6aa4691e`` (XML)
   and ``b9d9bbe82bc4a68d367a8cb00a0a22892b0b1cb516510fd0459d1df6805f059f``
   (``noxml``), byte-identical to the ZIP-extracted copy.
#. The verdict is stated plainly, including if it is "the claim was true".

U3 -- the seven-step verification driver
========================================

:Serves: PHASE-00 gate item 8, first branch
:Wave: B (depends on U1, U2)

One script implementing all seven checklist steps, each capturing its evidence
into a transcript.

Acceptance conditions
---------------------

#. ``scripts/ci/windows-percolator-verify.sh`` exists and is executable, and
   is a thin wrapper: the work is in ``scripts/ci/windows_percolator_verify.py``
   so that no logic depends on Git Bash behaviour.
#. All seven steps are implemented, in order, each writing to the transcript:

   #. download ``percolator-v3-07.exe`` and require SHA-256
      ``a9860e02a7e78b9bc069438e6564eb20e90bb46244aa628d567e4b69fe1ea348``;
   #. extract the NSIS payload -- **not** install it -- and require the
      payload binary's SHA-256 to be
      ``044f3957e2f05a38d13d8c77136f24435827d8563850b8808b5ad52e6aa4691e``;
   #. capture the whole of ``percolator.exe --help``;
   #. generate the 400-PSM PIN with U1's generator, run
      ``percolator.exe -X pout.xml test.pin``, and record the exit code,
      whether ``pout.xml`` exists, its size, its first ten lines and its
      ``<psm>`` count;
   #. run ``percolator.exe --xml-in test.pin`` and record whether
      ``Compiler flag XML_SUPPORT was off`` appears. It must **not**. This is
      the discriminating test;
   #. record whether any step needed elevation, and whether the account is an
      administrator;
   #. write the transcript.

#. Every subprocess is launched with an argument array and a timeout. A hung
   binary is recorded as a timeout, not as a pass.
#. **A negative result fails the job and says why.** The verdict block
   distinguishes a harness failure (download, checksum, extraction) from a
   negative finding about the binary, and neither is reported as success.
#. Exit code 0 is never the evidence: every assertion names the value it
   observed.
#. On a non-Windows host the script refuses by default with a clear message,
   and ``--check-only`` runs every platform-independent step so the harness
   can be exercised here.
#. The transcript records the SHA-256 of the generated PIN and whether it
   matches the pinned Linux value, so any cross-platform comparison carries
   its own caveat.

U4 -- the workflow, and the gate that guards it
===============================================

:Serves: PHASE-01 gate item 6, PHASE-00 gate item 8
:Wave: C (depends on U3)

Acceptance conditions
---------------------

#. ``.github/workflows/windows-percolator.yml`` runs on ``pull_request`` to
   ``main`` and on ``workflow_dispatch``, on ``windows-latest``, with
   ``permissions: contents: read``.
#. Every action is pinned to a full 40-character commit SHA.
#. The transcript is uploaded as an artifact **even when the job fails**;
   otherwise a negative result is the one result that does not get uploaded.
#. ``scripts/ci/check-workflows.py`` checks the new file. It currently
   iterates a fixed tuple of three names, so a fourth workflow would be
   unchecked -- that hole is closed by discovering every file in
   ``.github/workflows/`` and failing on one it does not know, rather than by
   adding a fourth name.
#. Any relaxation the new file needs -- a second permitted action, a
   permitted ``if:`` value -- is expressed as a narrow allowlist and given its
   own self-test case proving that anything outside it is still rejected.
   ``release.yml`` keeps its "checkout only, no secret, no push" rule exactly.
#. ``bash scripts/ci/check-workflows.sh`` passes and
   ``--self-test`` reports **more** damaged copies rejected than the nine it
   reports today, never fewer.
#. ``scripts/ci/run-pipeline-locally.sh`` covers the new workflow and records
   its Windows steps as NOT RUN on this machine.
#. A ``.gitattributes`` forces LF on ``*.sh`` and ``*.py``. GitHub's Windows
   runner image sets ``core.autocrlf=true``; a shell script checked out with
   CRLF fails under ``bash`` with ``$'\r': command not found``, and the
   existing nightly Windows job would hit the same wall.
#. ``bash scripts/build.sh`` still reports ``11/11 stages OK``.
