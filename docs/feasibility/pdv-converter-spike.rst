What this proves, and what it does not
======================================

Two things were asked for and both were obtained on this Linux host on
2026-08-29, from one re-runnable script:

#. The pinned Limelight converter JAR's **real** argument list, taken from its
   own ``--help``, quoted verbatim below, compared row by row against the
   specification's table.
#. **Real figures generated by PDV 2.7.0's command-line mode** from the Comet
   pepXML that work unit 8 produced, together with the matching spectra. Nine
   image files were produced across three runs and every one of them was
   re-read from disk and parsed from its own header: five PNGs at 800x400
   pixels and four PDFs at 576x288 pt (the PDF run repeats four of the PNG
   run's figures in a different format).

Four findings matter more than the two boxes ticked, and each is a product
constraint rather than a curiosity:

#. **PDV's "CLI" mode is not headless.** ``PDVCLI.PDVCLIMainClass`` extends
   ``javax.swing.JFrame``, so the process dies with a ``HeadlessException``
   before it parses a single argument if no display is available. CometGUI will
   launch PDV as a child process; on a user's desktop this is satisfied, but it
   rules PDV out of any headless CI job that does not provide a virtual display.
#. **PDV 2.7.0 cannot find spectra in an mzML whose scan numbers do not start
   at 1**, and it exits **0** while writing no figure. This is the single most
   important finding in this document: our input is a scan-range subset
   (instrument scans 11187-11987), PDV asks the mzML parser for scan 11892, and
   the parser numbers spectra by their 1-based position in the file (1..801).
   The lookup misses and PDV reports success.
#. **Converting the mzML to MGF makes it work**, because the MGF path keys
   spectra by title and Comet records the mzML native id in the pepXML. The
   conversion is a plain re-encoding of the same peaks.
#. **The converter exits 0 when required arguments are missing**, so its exit
   status alone is not a success signal either. Two tools in this chain now
   share that defect; the specification's warning about exit codes is not
   theoretical.

What this document does **not** establish: nothing was run on Windows or
macOS; PDV's GUI was not driven; and no claim is made about mzML files other
than the two fixture files. Every item that could not be established is listed
under `What is UNVERIFIED`_.

A defect a launcher must not trip over
--------------------------------------

The converter's exit status does not distinguish "did the work" from "was
invoked wrongly":

.. list-table::
   :header-rows: 1
   :widths: 58 12 30

   * - Invocation
     - Exit
     - Behaviour
   * - ``--help`` / ``--version``
     - 0
     - prints and exits, as expected
   * - no arguments at all
     - **0**
     - prints ``Missing required options: '--comet-params=...',
       '--percolator-file=...', '--out-file=...'`` followed by the usage block,
       and exits **successfully**
   * - an unrecognised option (``--bogus-option``)
     - **0**
     - same
   * - required options present but the files do not exist
     - 1
     - fails properly

So a run that produced nothing because the argument array was built wrongly is
indistinguishable, by exit status, from a successful conversion. CometGUI must
verify that the output file exists and parses, exactly as work unit 8's script
does. Combined with the ``Error printing runtime information.`` line the
converter prints on standard output on every run, neither the exit code nor the
absence of stdout content can be used as the success test.

How the CLI is actually entered
-------------------------------

There is no separate CLI launcher. The JAR manifest reads::

   Main-Class: PDVGUI.gui.PDVMainClass

``PDVGUI.gui.PDVMainClass.main`` inspects its arguments and, when any are
present, constructs ``PDVCLI.PDVCLIMainClass``. That class has **no** ``main``
method of its own -- ``java -cp PDV-2.7.0.jar PDVCLI.PDVCLIMainClass`` fails
with "Main method not found in class PDVCLI.PDVCLIMainClass". The only correct
invocation is::

   java -jar PDV-2.7.0.jar <options>

with at least one option; with none, the GUI starts.

It needs a display, and that is not negotiable
----------------------------------------------

``PDVCLI.PDVCLIMainClass`` extends ``javax.swing.JFrame`` and the frame is
constructed at the very top of its constructor, before any argument is read.
On this host, which has no X display, even ``-h`` fails::

For the product this means: PDV's figure generation is fine on a user's
desktop, and is **not** usable from a headless build agent unless that agent
provides a virtual display.

The mzML path is broken on this input, and it exits 0
-----------------------------------------------------

The obvious command -- the Comet pepXML plus the very mzML Comet searched --
produces nothing::

   java -jar PDV-2.7.0.jar \
       -r scratch/scientific-path/comet/20100614_Velos1_TaGe_SA_K562_3.pep.xml -rt 2 \
       -s scratch/scientific-path/mzml-lf/20100614_Velos1_TaGe_SA_K562_3.mzML -st 2 \
       -i peptide.txt -k p -o out -ft png

Standard output::

   The spectrum key is 11892
   The spectrum key is 11365
   The spectrum key is 11367
   The spectrum key is 11907

   exit status 0

``out/`` contains no figure at all -- only ``error.txt``::

   20100614_Velos1_TaGe_SA_K562_3.mzML_cus_705	 No spectrum
   20100614_Velos1_TaGe_SA_K562_3.mzML_cus_178	 No spectrum
   20100614_Velos1_TaGe_SA_K562_3.mzML_cus_180	 No spectrum
   20100614_Velos1_TaGe_SA_K562_3.mzML_cus_720	 No spectrum

PDV found the four PSMs for the peptide correctly. It failed to fetch their
spectra, and reported success.

**The cause**, established by reading PDV's bytecode and then confirming it
against the library directly. ``PDVCLI.PDVCLIMainClass.processSpectrumFile``
loads an mzML through ``umich.ms.fileio.filetypes.mzml.MZMLFile`` (the msftbx
library, ``lib/msftbx-1.8.8.jar``) into a ``ScanCollectionDefault``.
``buildScanSpectrum`` then does, in effect,
``scans.getScanByNum(Integer.valueOf(key))`` where ``key`` is the pepXML's
``start_scan`` -- the instrument scan number. But msftbx numbers spectra by
their **1-based position in the file**. A direct probe against
``lib/msftbx-1.8.8.jar``, with the same load parameters PDV uses, shows both
halves of the mismatch:

.. list-table:: Probe against the fixture mzML (801 spectra, instrument scans 11187-11987)
   :header-rows: 1
   :widths: 46 54

   * - Query
     - Result
   * - index map size
     - 801
   * - ``getMapById()`` entry for ``controllerType=0 controllerNumber=1
       scan=11382``
     - ``number = 196`` -- the file position, not 11382
   * - ``getScanByNum(11892)`` (what PDV asks for)
     - ``NULL``
   * - ``getScanByNum(11367)``
     - ``NULL``
   * - ``getScanByNum(706)`` (the same spectrum by position)
     - found, ``msLevel=2``, ``mzTarget=504.230010986328``, 136 peaks
   * - ``getScanByNum(196)``
     - found, ``msLevel=2``, ``mzTarget=441.408172607422``, 167 peaks

The precursor m/z of position 706, 504.23, is exactly what PDV printed for
scan 11892 once the MGF path made the same spectrum reachable, which closes the
identification.

Note the two numbers in play, because they show the inconsistency is internal
to PDV rather than a property of the input. The lookup PDV performs uses the
instrument scan number (``The spectrum key is 11892``), while the key it names
in ``error.txt`` uses the mzML's own 0-based ``index`` attribute
(``_cus_705``; 11892 minus 11187 is 705). msftbx, meanwhile, numbers the same
spectrum 706 -- 1-based position. Three numbering schemes for one spectrum, and
the one PDV asks with is the only one msftbx does not answer to. Exactly which
line of PDV emits each of the two keys was not pinned down, and does not need
to be: the failing lookup and its cause were both observed directly.

**When this bites.** In a full-run mzML the first spectrum is usually scan 1
and the numbering is contiguous, so position and scan number coincide and
PDV's assumption holds by accident. Our fixture is a scan-range subset
(``20100614_Velos1_TaGe_SA_K562_3.mzML`` starts at instrument scan 11187), and
the two diverge by a constant 11186. Any real-world mzML that is a subset, or
that has had scans filtered out, will hit this. **This was not verified against
a full-run mzML**, so the "usually works" half of that sentence is a prediction,
not an observation.

The route that works: MGF
-------------------------

PDV's MGF path keys spectra by *title*, and the key it builds is::

   <spectrum file name>_cus_<pepXML spectrumNativeID>

which was read straight off PDV's own stdout::

   The spectrum key is 20100614_Velos1_TaGe_SA_K562_3.mgf_cus_controllerType=0 controllerNumber=1 scan=11367

Comet records the mzML's native id in every ``spectrum_query`` as
``spectrumNativeID="controllerType=0 controllerNumber=1 scan=11367"``. So an
MGF whose ``TITLE`` is the mzML native id -- which is what a conventional mzML
to MGF conversion writes -- is found immediately. No identifier was invented:
the title is copied from the mzML's own ``id`` attribute.

``scripts/feasibility/pdv_spike_helpers.py mgf`` does that conversion in pure
Python (base64, optional zlib, 32- or 64-bit little-endian floats). For the
fixture it writes 728 MS2 spectra, 1,216,487 bytes, with none skipped -- 728 is
also exactly the number of ``spectrum_query`` elements in the Comet pepXML,
which is the cross-check that nothing was dropped. The first entry::

   BEGIN IONS
   TITLE=controllerType=0 controllerNumber=1 scan=11188
   PEPMASS=615.788391
   CHARGE=2+
   RTINSECONDS=4740.956
   ...

intensity axis to 100 and an m/z axis to 1,500. Text renders correctly, which
matters because this host has no system fonts.

Selecting by spectrum id rather than peptide
--------------------------------------------

``-k s`` expects the pepXML's ``spectrumNativeID`` **value alone** in the
``-i`` file, not the composite ``<file>_cus_<id>`` key that PDV prints::

   printf 'controllerType=0 controllerNumber=1 scan=11188\n' > spectrum-id.txt
   java -jar PDV-2.7.0.jar ... -i spectrum-id.txt -k s -o out -ft png

produces one verified figure,
``WIDNPTVDDRcontrollerType=0 controllerNumber=1 scan=11188.png``, 15,961 bytes,
PNG 800 x 400, 494 distinct colours, 8,295 non-white pixels. Supplying the
composite key instead writes ``... No result`` to ``error.txt`` and produces
nothing, again with exit status 0.

This is the mode CometGUI would use to render one selected PSM, and it is the
mode that matters for ``D-005``.

Other output formats
--------------------

``-ft pdf`` on the same four PSMs produced four PDFs, each ``%PDF-1.4`` with a
correct trailing ``%%EOF`` and ``/MediaBox`` 576 x 288 pt (that is 800 x 400 px
at 72 dpi), 41,057 to 64,348 bytes. ``tiff`` and ``report`` are offered by the
help text and were **not** exercised.

``-rt 6`` (TIC) was exercised and **hangs**: with ``-rt 6 -s <mzML> -st 2 -o
<dir> -ft png`` the process was still running after 600 seconds, having written
nothing, and had to be killed. Whatever that mode needs, it is not what the
help text implies, and a launcher must impose a timeout on PDV rather than
waiting on it.

interactive; batching several spectra into one invocation is far cheaper.

across cores; on a two-core laptop the wall time will be worse.

What PDV needs to run
---------------------

       (Liberica 25.0.4.1+1) for everything in this document. No
       ``--add-opens`` or ``--add-exports`` flag was needed for the MGF path.

     - **Required.** Swing/AWT; ``HeadlessException`` without one, before

   * - X11 client libraries
     - Required, because AWT loads ``libawt_xawt.so`` which needs
       ``libX11.so.6``. This host has none, so the project-local closure under

       Present by definition on a real desktop.

     - At least one real font is needed to draw the annotations. On this host
       the only font files are the project-local DejaVu copies that came with

       correctly. See `What is UNVERIFIED`_ for what could not be pinned down.

       No ``-Xmx`` was set; a bigger run should be measured before a limit is
       chosen.

     - MGF works. mzML fails on a scan-number-offset file, silently. mzXML was
       **not** tested.

malformed ZIP central directory (``Invalid CEN header (invalid zip64 extra data
field size)``). JDK 25's ``javac`` and ``javap`` refuse to read it and abort
when it is on their classpath. ``java -jar`` tolerates it -- every run above
succeeded -- but any build- or analysis-time tooling that walks PDV's classpath
will trip over it.

Part 3 -- evidence for D-005 (not an answer)
============================================

``D-005`` asks whether release 1 needs exact click-a-row-to-update-PDV
selection, and records as fact: "PDV supports the needed file formats, but its
documented external control server is de novo specific. A generalised
database-search control mode does not exist upstream."

.. note::

   This section is evidence and costed options only. ``D-005`` is the owner's
   to answer; nothing here should be read as a decision.

What this work unit can confirm from the artefact itself
--------------------------------------------------------

**The decision's stated fact still holds today, and can now be made sharper.**
The external control server exists, it is real, and it is reachable only
through the de novo entry point.

Checked directly against the shipped artefact on disk -- the class list and the
string constants of ``PDV-2.7.0.jar`` -- and against the running program, not
against documentation:

.. list-table:: What ships in PDV 2.7.0
   :header-rows: 1
   :widths: 34 66

   * - Observation
     - Where it was seen
   * - A control server class exists
     - ``PDVGUI/gui/utils/PdvControlServer.class`` -- the only class in the
       release whose name contains ``Control`` or ``Server``
   * - Its endpoints are ``/ready``, ``/select`` and ``/shutdown``
     - string constants inside ``PdvControlServer.class``
   * - It is bound to loopback and driven by ``--port``
     - ``127.0.0.1``, ``--port``, ``--hide-psm-table``, ``--mztab`` and
       ``denovo-gui`` are all string constants of
       ``PDVGUI/gui/PDVMainClass.class``, and of no other class
   * - Selection is keyed on the mzTab ``spectra_ref``
     - ``spectra_ref`` appears in ``PDVGUI/fileimport/MztabImport.class`` and
       in one inner class of ``PDVMainClass``, and nowhere else in the release
   * - The subcommand exists and is mzTab-only
     - ``java -jar PDV-2.7.0.jar denovo-gui`` exits 1 with
       ``Usage: java -jar PDV.jar denovo-gui --mztab <file.mztab> --spectrum
       <f1.mzML[,f2.mzML]> [--tol <value>] [--tol-unit Da|ppm] [--port <p>]
       [--hide-psm-table]``
   * - The batch CLI has no such door
     - the full option list quoted earlier in this document contains no port,
       listener, server or interactive-mode flag; the absence is complete

So an external launcher *can* drive a running PDV -- but only one launched as
``denovo-gui --mztab ... --port <p>``, and selection is by mzTab
``spectra_ref``. A Comet + Percolator run produces pepXML and Percolator XML,
never mzTab, so **there is no path from CometGUI's results to that server**
without inventing an mzTab export, which would then be a de novo-shaped file
describing a database search.

The same conclusion from a second direction: PDV's database-search results
reach the GUI through the Database Searching dialog and the batch CLI, and
neither takes a ``--port``. Upstream research on 2026-08-29 additionally found
that the ``spectra_ref`` index the ``/select`` endpoint resolves against is
populated only by the mzTab importer, so a pepXML import would leave ``/ready``
answering 503 indefinitely; that read of the source is second-hand here and is
listed under `What is UNVERIFIED`_, but it is consistent with every string
constant checked above.

Two further upstream facts, verified first-hand today:

* **2.7.0 is still the newest release.**
  ``https://github.com/wenbostar/PDV/releases/latest`` redirects to
  ``.../releases/tag/v2.7.0``, published ``2026-08-14T19:55:27Z``. The version
  work unit 2 pinned is current.
* **No upstream request for generalised external control.** A search of the
  issue tracker (open and closed, issues and pull requests) found no issue
  asking for programmatic or external control of PDV for database-search
  results. The nearest neighbours are both open CLI-batch requests -- #103,
  "Request for Adding Command-Line Report Export Functionality" (2026-03-30, no
  reply) and #94, "mirror plots - command line" (2025-08-31), answered by the
  maintainer on 2025-10-06 with "It's not supported in the current version".
  That search was performed by a research agent rather than by this work unit's
  own hands; see `What is UNVERIFIED`_.

The options, with costs
-----------------------

.. list-table::
   :header-rows: 1
   :widths: 22 26 26 26

   * - Option
     - What the user gets
     - Cost
     - Risk
   * - **A -- baseline only**
       (open-in-PDV plus CLI figure generation)
     - A button that launches PDV on the run's results, and a
       "save figure for this PSM" action that shells out to the CLI. No live
       coupling: selecting a different row in CometGUI does not move PDV.
     - Low. The CLI contract is now known exactly and is proven working: one
       process per request, ~2 s each. Needs an mzML-to-MGF step (see below),
       a timeout, and output-file discovery by directory scan rather than by
       predicted name.
     - Low. Everything it depends on was executed today. The residual risks are
       PDV's silent-success behaviour and the mzML defect, both of which the
       product can detect.
   * - **B -- baseline plus an upstream contribution**
     - Eventually, real click-a-row selection for everyone, upstream.
     - Cheaper than it looked on 2026-08-28, because the mechanism already
       exists and would be *extended*, not invented: a ``db-gui`` sibling of
       ``denovo-gui``, and a ``spectra_ref``-equivalent index populated by the
       pepXML importer instead of only by the mzTab importer. Upstream added
       the whole server in a single commit in June 2026, for CasanovoGUI, which
       is a comparable third-party launcher -- so there is precedent for
       accepting exactly this kind of change. Still: design, implementation and
       review in a codebase this project does not own.
     - High **for release 1**, because merge and release timing belong to a
       third party, not because the change is large. Sound as a release 2 goal
       layered on top of A. If it is attempted, do it as an upstream pull
       request, not a private patch.
   * - **C -- baseline plus a small maintained fork**
     - Real click-a-row selection, on the project's own schedule.
     - Baseline, plus a fork of a Java 8 application with 183 bundled
       dependency jars, a build for it, and redistribution of a modified PDV.
       PDV is **GPL-3.0** (verified above), so redistributing a modified build
       carries the GPL's source-availability and licence-compatibility
       obligations -- a question for ``D-003``/``D-001``, not for an agent --
       and it adds a second Java application to the packaging and provenance
       story for every platform.
     - Medium-high and permanent: every upstream PDV release must be re-merged,
       and CometGUI's provenance record would have to describe a binary that
       exists nowhere else.

Two constraints that apply to **every** option, and are the real news from this
work unit:

#. **Whatever the integration level, the product needs an mzML-to-MGF step for
   PDV**, or a way to detect that an mzML's scan numbering will defeat it. This
   is not optional and is not related to ``D-005``: even option A cannot draw a
   figure from a subset mzML.
#. **PDV needs a display.** That is free on the user's desktop and fatal in
   headless CI, so the acceptance tests that exercise the PDV integration must
   either provide a virtual display or assert on the launcher's argument array
   rather than on PDV's output.

Screen-coordinate automation is not costed here. ``D-005`` already records that
it must not be substituted, and nothing observed today changes that.

What is UNVERIFIED
==================

Stated plainly, because an unverifiable item is not a passed item.

#. **Which licence upstream means.** The ``LICENSE`` file at tag ``v2.7.0``
   says GPL-3.0 and ``pom.xml`` at the same tag says Apache-2.0. Both were read
   today; the contradiction is upstream's, and this work unit cannot resolve
   it. Treating PDV as GPL-3.0 is the safe reading, not a verified fact about
   the maintainer's intent.
#. **Second-hand upstream findings.** Three claims in Part 3 come from a
   research agent's reading of upstream sources rather than from this work
   unit's own hands: that the ``/select`` endpoint resolves only against an
   index populated by ``MztabImport``; that no issue or pull request in the
   tracker asks for generalised external control; and the quoted text of
   issues #103 and #94. The quoted 2.7.0 release-note line about mzML imports
   failing on Java 16 and newer is second-hand in the same way. Each is
   consistent with what was verified directly
   against the shipped jar, but each should be re-checked before it is relied
   on in a decision.
#. **Whether a full-run mzML works.** The prediction that PDV's mzML path
   succeeds when position and scan number coincide follows from the mechanism
   but was **not** demonstrated: no full-run mzML was available.
#. **mzXML input** (``-st 3``) was not tested at all.
#. **``-ft tiff`` and ``-ft report``** were not tested.
#. **Where AWT found its fonts.** Removing ``FONTCONFIG_PATH`` and
   ``XDG_DATA_HOME``, and running with an empty ``HOME``, still yielded the
   same eight font families and a byte-identical PNG, even though this host has
   no ``/etc/fonts``, no ``/usr/share/fonts`` and no user font directory. The
   font files can only have come from the project-local closures, but the
   resolution path was not established. The practical claim -- "PDV needs at
   least one font present" -- is therefore *inferred*, not proved; a host with
   genuinely zero font files was never tested, because the X11 closure PDV
   needs for its display also carries DejaVu.
#. **The ``-rt 6`` (TIC) hang** was observed once, at 600 s, on one file. The
   cause was not diagnosed.
#. **PDV memory ceiling.** Only an 11 MB spectrum file was used. No ``-Xmx``
   was tuned and no large-file measurement was taken.
#. **Windows and macOS.** Nothing in this document was executed on either.
   PDV is a pure-Java Swing application, so it is expected to behave the same,
   but expectation is not evidence.
#. **Multi-file runs.** Only ``..._3`` was used. Whether PDV can be pointed at
   a two-file search's pepXML plus the right spectrum file per PSM was not
   tested.

Reproducing all of this
=======================

::

   bash scripts/feasibility/pdv_spike.sh

It needs work unit 8's outputs on disk (regenerate with
``bash scripts/feasibility/run_scientific_path.sh``) and work unit 7's X11
closure under ``tools/`` (regenerate with
``bash scripts/feasibility/javafx-smoke.sh`` then
``bash scripts/feasibility/javafx-headed-xvfb.sh``). It fetches PDV once,
verifies its SHA-256 and byte count, unpacks it with Python's ``zipfile``,
starts and stops its own Xvfb on a free display, and runs ten stages:

#. the converter's ``--help`` and ``--version``, checking every documented
   option is present, plus the missing-argument exit-status defect;
#. fetch and verify PDV;
#. the headless negative control -- it **requires** the ``HeadlessException``;
#. start Xvfb;
#. PDV's own usage text;
#. the mzML attempt -- it **requires** exit 0 with no figure, so if upstream
   ever fixes this the stage fails and the document must be revisited;
#. mzML to MGF;
#. PNG generation by peptide, with every file verified from its header;
#. PNG generation by spectrum id;
#. PDF generation.

It exits non-zero if any stage fails, and each figure is re-read and parsed
rather than counted, because exit code 0 proves nothing.
